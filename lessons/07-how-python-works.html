Under the hood

How Python works

When you press run, your text file does not go straight to the computer. It travels through a short pipeline: tokens, a tree, bytecode, and finally a virtual machine. By the end of this page you will have watched each stage happen.

What you will learn

Why Python is both compiled and interpreted, what bytecode and .pyc files are, what the Python Virtual Machine does, and why "Python is just interpreted" is only half the story.

The short answer

People often say "Python is an interpreted language". That is only half true. The standard Python (called CPython) does two jobs every time it runs your code:

1. Compile

Your source code is translated into bytecode, a compact set of instructions made for Python's own virtual machine.

2. Interpret

The Python Virtual Machine reads the bytecode one instruction at a time and carries each one out.

So the accurate sentence is: Python compiles your code to bytecode, then interprets that bytecode. The compile step is invisible and very fast, which is why it feels like there is none.

How to read the Bytecode tab

ColumnMeaning
First number (for example 1)The line of your source code that produced the instructions. It appears only on the first instruction of each line.
Second number (for example 4)The instruction's position (offset) in the bytecode, counted in bytes.

Try the preset "Constant folding". You wrote 2 + 3, but the bytecode contains LOAD_CONST 5 and no addition at all. The compiler did the math ahead of time, so the work happens once, not every time the program runs. The AST tab still shows the original 2 + 3, because folding happens later, in the compiler.

Now try "A syntax error". Nothing is produced at all: the tokenizer and parser fail first, which is why a syntax error stops your whole file before any line runs.

Inside the virtual machine

CPython's virtual machine is a stack machine. It keeps a stack of values (like a pile of plates: you only touch the top one) and a table of variable names. Each bytecode instruction does one small thing to them. Step through the same program as before.

Three ideas to take from the animation:

  • LOAD instructions push, STORE instructions pop. total = a + b becomes: push a, push b, add (pops two, pushes one), store as total.
  • Names live in a table, not in the stack. At module level, each variable name is an entry in a dictionary that maps the name to a value. The next lessons on variables and memory build on this.
  • A function call is also just stack work: push the function, push the arguments, then CALL. Even print is looked up by name like any other variable.

The animation is simplified, but the instruction sequence is what CPython 3.12 produces for this program: press Show real bytecode under the animation to compare. Exact instructions change between Python versions, which is why bytecode is not portable across versions.

What is a .pyc file?

Compiling is fast, but doing it for every imported module on every run would be wasteful. So when you import a module, CPython saves its bytecode into a folder called __pycache__:

project/
├─ main.py
├─ utils.py
└─ __pycache__/
   └─ utils.cpython-312.pyc
  • Name: utils.cpython-312.pyc means: module utils, compiled by CPython 3.12. A different Python version would make a different file.
  • Contents: a small header (a magic number that identifies the bytecode version, flags, and the source file's modified time and size, or a hash) followed by the compiled code object.
  • Reuse: next time, if the source file has not changed, Python loads the .pyc and skips the tokenizer, parser and compiler.
  • Not for the script you run directly. python main.py compiles main.py in memory each time. Only modules it imports get cached.
  • Safe to delete. Python recreates the files when needed. You normally add __pycache__/ to .gitignore.

A common myth: .pyc files do not make your program run faster once it is going. They only make starting and importing faster, because the compile step is skipped.

Peek at a code object

compile() gives you the compiled code object directly. Its fields hold the constants, the names, and the raw bytecode bytes.

So, does the CPU run bytecode?

No, and this is the most common misunderstanding. Bytecode is not machine code for your processor. It is a list of instructions in a format only the Python Virtual Machine understands. Your CPU runs something else: the CPython interpreter, which is itself a program written in C and compiled to ordinary machine code. That program contains a big loop that reads bytecode and acts on it.

Your codetotal = a + b, a text file you wrote
compiled by CPython to
BytecodeLOAD_NAME, BINARY_OP, ... instructions for the Python VM
read by
The CPython interpretera C program: the evaluation loop (in CPython's source this lives in ceval.c)
which is machine code run by
The CPUthe only layer that deals in real machine instructions

That extra layer is also why plain Python is slower than a language compiled straight to machine code: every operation goes through the interpreter loop. Libraries such as NumPy are fast because the heavy work is done in compiled C, not in Python bytecode.

Recap

  • CPython compiles your source to bytecode, then the Python Virtual Machine interprets it.
  • The pipeline: source, tokens, AST, bytecode, virtual machine, output. Syntax errors come from the early stages, before anything runs.
  • The VM is a stack machine: LOAD pushes, STORE pops, and names live in a table.
  • .pyc files cache bytecode of imported modules in __pycache__. They speed up startup, not execution.
  • Bytecode is not machine code. Your CPU runs the CPython interpreter, which runs your bytecode.
